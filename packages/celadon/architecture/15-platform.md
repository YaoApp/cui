# 15 · 平台层

- **版本**：v1.41
- **最后修改**：2026-10-03 10:58:09
- **说明**：平台层：构成与落位 · 服务信息 · 凭据与鉴权 · 客户端 · 客户端底座（Bridge）· 测试

## 1. 规则

- **平台层不认识业务词汇**：只存**通用事实**（主题 · 语言 · 凭据 · 客户端 · 服务信息），不存某个功能的字段（同 `06-state.md` 的判据）。
- **宿主差异只在这一层消化**：Web 与 Desktop 的差别（鉴权载体 · 能力开关）**不许渗到 feature**。
- **单一来源不在这里重定义**：颜色/间距在 `theme/`（源头 `design/`）· 文案在语言包 · 图标产物由脚本生成（见 `09` · `08` · `10`）。
- **服务信息只读**：`/.well-known/yao` 的内容由后端给，应用**只读不写**。
- **鉴权按宿主选载体**：**Web 用服务端的安全 Cookie**（前端不接触凭据）· **Desktop 用 token 直连**，不要求宿主起代理（见 §4）。
- **宿主能力只在 `bridge/` 实现**：凭据读写 · 本地服务 · tai · 更新 · 环境 · 隧道 · 系统集成都在那里，
  **只有它调 `invoke`**；其它层只调用，不许出现 `@tauri-apps/api`（见 §6）。
- **命令名集中在 `bridge/` 一处**；**类型与 Rust 一一对应**，`Result<T, String>` 映射成统一错误形状（同 §4.4 的错误归一）。
- **平台差异在 Rust 里消化**：各平台实现对外**函数名与签名完全一致**，TS 层不许写平台判断；**Windows 原生运行，不引入 WSL**。
- **`bridge/` 在 Web 下不存在**：调用方**先问 `client/` 的能力开关**（见 §5），不许直接调再捕获异常。
- **状态靠订阅，不靠轮询**：服务状态变化由 Rust 推事件。
- **危险动作要先确认**：启停服务 · 更新 · 隧道。

## 2. 构成与落位

| 构成 | 管什么 | 形态 |
| --- | --- | --- |
| `theme/` | 主题偏好（三态）· 解析后的主题 · 对比度工具 | 公共态 + 纯函数 |
| `router/` | basename · 页标题 · URL 绑定 | 纯函数 + 钩子 |
| `i18n/` | 语言包加载 · 语言偏好 · 语言解析 | 公共态 + 纯函数 |
| `icons/` | 图标产物（生成）· 底座挂载 | 生成物 + 挂载 |
| `utils/` | 纯函数与常量（导航 · 可读色 · 分享链接） | 纯函数 |
| `service/` | **服务信息**：读 `/.well-known/yao` 并缓存（见 §3）| 公共态 + 取数 |
| `credential/` | **凭据的存取与消费**：读写 · 续期 · 由凭据推出的当前身份（见 §4）| 公共态 + 宿主实现 |
| `client/` | **客户端信息**：客户端类型 · 能力开关 · UA 解析 · 客户端标识（见 §5）| 纯函数 + 常量 |
| `transport/` | **统一出口**：http(s) 与 ws(s) 的唯一封装（见 §4.4）| 纯实现 |

**落位判据**：平台层内部**向下依赖**（`utils/` 不依赖其它；`credential/` `client/` `transport/` `bridge/` `webproxy/` 可依赖 `utils/`）。

## 3. 服务信息（well-known）

**启动时读一次** `GET /.well-known/yao`，结果进公共态并缓存。

| 字段 | 用途 |
| --- | --- |
| `name` · `version` · `description` | 关于页 · 上报 |
| `openapi` | **接口根**（如 `/v1`）—— 所有请求以它为前缀 |
| `issuer_url` · `server_url` | 鉴权与接口的服务地址 |
| `webproxy`（`domain` / `prefix` / `protocol`）| agent sandbox 服务访问代理的域名构造规则（见 §4.3）|
| `license` | 能力开关（`valid` / `edition`）|
| `tao` | 注册 / 升级入口 |
| `developer` | 关于页署名 |
| `disable_system_setting`（默认 `false`）| 为 `true` 时禁掉「系统设置」入口 |
| `disable_dashboard`（默认 `false` · **待后端实现**）| 为 `true` 时关掉管理端能力（见 §3.1）|
| `client_ip`（**待后端实现**）| **后端在响应里给出它看到的调用方地址**；应用只读，不自己探测（见 §5.2）|

- **每个开关都要标明默认值**，前端按默认值行为。
- **读不到 well-known 时转向统一提示页**，不白屏、不用默认值继续跑。

### 3.1 能力被关掉、或服务信息取不到时

- **以响应为准**：能力开关只认 well-known 与接口返回，前端不自行假设。
- **`disable_dashboard: true`（纯 SUI 站点）**：管理端相关接口全部关闭（后端负责）；前端不进入那些界面，访问到相关地址时转向统一提示页。
- **`disable_system_setting: true`**：只关「系统设置」入口，其余照常；入口**不渲染**。
- **统一提示页只有一处**：取不到 well-known、`disable_dashboard`、其他致命启动失败，都转到同一个页面。
- **提示页是界面**：`platform/` 只把开关与失败原因读进公共态，页面由路由/界面层给。
- **不为旧版服务端做兼容**：V2 与配套服务端成对发布，不满足要求时走统一提示页。

## 4. 凭据与鉴权（`credential/`）

**两种凭据载体，按宿主选**：

| 宿主 | 换取 | 载体 | 谁持有 |
| --- | --- | --- | --- |
| **Web** | `POST …/login/web` | **安全 Cookie**（服务端下发 · HttpOnly）| 服务端会话；前端不接触凭据 |
| **Desktop** | `POST …/login/token` | **Bearer token** | 宿主本地（见 §4.5）|

- **Web 一律走 Cookie**：前端不读、不写、不存令牌；是否已登录**向服务端查会话**，不靠本地推断。
- **Desktop 走 token**：请求在 Rust 侧发出（见 §4.1），`Authorization: Bearer <access_token>`；**调用方已显式带 `Authorization` 时不覆盖**（登录第一步用一次性临时 token）。
- **两步登录**：① 验证账号存在 → 拿临时 token（可能要先过验证码）② 换取凭据（Web 得 Cookie；Desktop 得 `access_token` + `refresh_token` + `session_id`）。
- **续期**：Web 由服务端会话决定；Desktop **启动时刷一次 + 之后每 6 小时一次**。
  失败不拦路由、不拦首屏（与未登录同待遇），**定时器只在 `credential/` 一处**。
- **接口根**取 well-known 的 `openapi`；取不到按 §3 走统一提示页。
- **凭据只由 `credential/` 一处存取**：读写 · 续期 · 清除；调用方只说"要一个可用凭据"。**feature 不许自己读、自己写**。
- **公共态只存通用事实**：当前用户（`id` · 显示名 · 头像）· 当前团队（`team_id`）· 登录状态，**由凭据推出**，随凭据一起失效；不存业务角色/权限。
- **未登录不是错误**：公共态为 `null`，界面按未登录渲染，不抛异常、不阻塞路由。

### 4.1 直连与跨域

| 宿主 | 发出请求的层 | 跨域 |
| --- | --- | --- |
| Desktop | **Rust 侧封装的 fetch** | **无** —— 直连服务端 |
| Web | 浏览器 `fetch()` | **有** —— 需同源部署或服务端 CORS |

- 服务端**不发 CORS 头、不处理预检**（`Access-Control-*` 全无、`OPTIONS` 返回 404）：浏览器里发出的跨域请求拿不到响应；不从浏览器发出就不受此限。
- Desktop 的请求**一律在 Rust 里发**，不用 webview 的 `fetch()`。
- Web 走 Cookie 时跨域请求需带凭据；生产同域部署不受影响（见 §4.2）。

### 4.2 后端地址（仅开发期）

- **生产同域**：`dist` 集成进 yao 后由服务端托管，接口一律用**相对路径**（`${openapi}/...`），应用代码不感知后端地址。
- **开发期**由 `.env` 给后端地址（dev server 的代理目标，键名 `YAO_SERVER_HOST`），应用代码不变。
- **不许**把后端地址编进应用代码，不许在业务里用 `import.meta.env` 拼绝对地址。

### 4.3 agent sandbox 的服务访问代理（`webproxy`）

- `webproxy` 的 `domain` / `prefix` / `protocol` 用来构造 **agent sandbox 内服务**的访问地址；sandbox 里的服务通过它挂在域名下被访问。
- 它与 §4.2 的后端地址无关：后者只属开发期，`webproxy` 是运行时。
- 构造规则归 `platform/webproxy/`（纯函数），消费方按需取用，不许各自拼字符串。

### 4.4 统一出口（`transport/`）

**所有对外通信都经这一层**，业务不直接 `fetch` / `new WebSocket`。

- **协议**：`http(s)`（含流式）· `ws(s)`，同一套鉴权、基址、错误归一。
- **一处承担**：基址解析 · 注入凭据（显式带的不覆盖）· **401 时刷新并重放** · 错误归一。
- **宿主差异只在实现里**：Web 用浏览器 `fetch` / `WebSocket`；Desktop 用 Rust 侧封装的 fetch + native WebSocket。
- **不规定上下文格式**：出站上下文的值由 §5.1 给，**带不带、怎么带由各 API 的接口封装决定**。
- **对外形状一致**：同一套方法签名与返回类型，feature 不感知宿主。
- **不许**：业务自己拼 URL、自己读 token、自己建 WebSocket、自己判宿主。

### 4.5 客户端凭据的存放

| 宿主 | 存哪 | 密钥归谁 |
| --- | --- | --- |
| **Web** | **不落盘** | 服务端会话（HttpOnly Cookie）|
| **Desktop** | **系统凭据库** | macOS 钥匙串 · Windows 凭据管理器 · Linux libsecret |

- **实现**：Rust 侧依赖 `keyring` crate（4.x · 仓库 `open-source-cooperative/keyring-rs`，按目标平台自动选后端），经 `bridge/` 的凭据域暴露（见 §6）；上层只经 `credential/`。
- **密钥不随密文走**：密文拷到另一台机器、或同一台机器的另一个系统账号，解不开。
- **不许静默退回明文**：系统凭据库不可用时，明确失败并提示，或用限权文件并告知。
- **保护范围是"密文被拷走"**：以该用户身份执行代码、或 dump 进程内存，仍能拿到令牌。

## 5. 客户端（web / desktop）

- **客户端类型由打包决定**：`client` 写在构建清单（`app/src/platform/manifest.json`，见 §5.3），`client/` 只读它。
- **不读框架内部变量**：`window.__TAURI__` / `window.__TAURI_INTERNALS__` 是框架实现细节，不能当约定用。
- **读取点只有一处**：只有 `client/` 读清单，别处不许再判宿主。
- **`client/` 暴露**：`client` · 能力开关（剪贴板 · 文件 · 通知 · 外部打开）· 宿主版本 · 客户端信息（见 §5.2）。
- **能力开关是唯一分支点**：feature 不许自己判宿主，要用能力就问 `env`。
- **不判 UA 猜宿主**：UA 可伪造且会漂。

### 5.1 出站上下文

**平台层提供一份出站上下文**，供后端做本地化与展示决策。

| 值 | 取值 | 来源 |
| --- | --- | --- |
| `locale` | `zh-CN` · `zh-TW` · `en-US` · `ja` | `i18n/` 的**解析结果**，不传 `'system'` |
| `timezone` | IANA 时区 | `Intl.DateTimeFormat().resolvedOptions().timeZone`，**调用时读** |
| `theme` | `light` \| `dark` | `theme/` 的**解析结果**，不传 `'system'` |
| `client` | `web` \| `desktop` | 构建清单（见 §5.3）|

- **载体不做统一规定**：字段名与传输形式（请求头 / 查询参数 / 请求体）**取决于对应 API 的要求**，在接口封装时定（见 §4.4）；平台层只保证值随时可取。
- **不另存一份**：`client/` 只汇总，不复制状态、不额外持久化。
- **拿不到就不带**：不编造。

### 5.2 客户端信息

**两个宿主导出的字段完全一致**，只有取值来源不同；上层只读导出结果，不判宿主、不管来源。UA 只在 `client/` 读一次，禁止其它层直接读 `navigator.userAgent`。

| 导出字段 | Web | Desktop | 说明 |
| --- | --- | --- | --- |
| `client` | `"web"` | `"desktop"` | 构建清单给（见 §5.3）|
| `os` | UA 解析 | 构建清单（见 §5.3）| `macos` · `windows` · `linux` |
| `ua` | UA 解析结果 | UA 解析结果 | 浏览器 · 系统 · 版本；给结果，不散播原始串 |
| `client_id` | `crypto.randomUUID()` 生成后存**本地存储** | 同 Web（webview 存储）| **UUID v4**；同一安装内不变 |
| `client_ip` | well-known 给出 | well-known 给出 | 后端在 well-known 里给出它看到的地址（见 §3）|

- **`client_id` 用 `crypto.randomUUID()`（UUID v4）**：**首次需要时生成**后存**本地存储**——
  **两个宿主都是 webview 存储，同一套代码**；**同一安装内不变**，清数据或换安装即更换。
  **它不是凭据**，不进系统凭据库（见 §4.5）。
- **`client_ip` 由后端给**：应用不自己探测公网地址，只读 well-known 里的值。
- **导出结构化字段，不照搬 UA 串**：UA 的格式是为历史兼容冻结下来的；需要单一客户端标识串时由 `client/` 拼。
- 这几项可作为出站上下文的一部分，是否带按 §5.1。

### 5.3 构建清单（`app/src/platform/manifest.json`）

放在 `platform/` 根下；开发时写好并进 git，CI 打包时改写成这一构建的事实。

| 字段 | 类型 | 开发时 | 打包时 | 用途 |
| --- | --- | --- | --- | --- |
| `version` | `string`（semver）| 手写当前版本 | 由发布 tag 改写 | 产品版本 |
| `commit` | `string`（短哈希）| `"dev"` | 本次提交哈希 | 定位构建来源 |
| `built_at` | `string`（ISO 8601 · UTC）| 写入时刻 | 构建时刻 | 对时间 |
| `client` | `"web"` \| `"desktop"` | `"web"` | 按打包目标 | **客户端类型**（见 §5）|
| `os` | `"macos"` \| `"windows"` \| `"linux"` | 空 | 桌面按打包目标写入 | 桌面目标系统；web 包不写（运行时解析，见 §5.2）|
| `artifact` | `"unified"` \| `"cui"` \| `"web"` \| `"yao"` \| `"tai"` \| `"server"` | `"web"` | 按打包目标 | **制品类型**，决定首页与管理入口（见 §6.2）|
| `build` | `"local"` \| `"ci"` | `"local"` | `"ci"` | 区分本地包与流水线包 |

- **只读**：运行时只读不写，要改就得重新构建。
- **只有 `client/` 读它**（见 §5）。
- **不放后端地址、不放密钥**：清单会进包。
- **`artifact` 六个取值**：`unified`（CUI + yao + tai）· **`cui`（仅桌面客户端，含 Bridge）**·
  **`web`（仅 Web，不含 Bridge）**· `yao`（仅 yao 管理）· `tai`（仅 tai 管理）· `server`（yao + tai 共享包）。
- **`artifact` 与 `client` 对齐**：含 Bridge 的制品 `client` 为 `"desktop"`，`web` 制品为 `"web"`。

## 6. 客户端底座（Desktop Bridge）

**桌面端宿主能力都在 `bridge/` 里实现**：凭据读写 · 本地服务 · tai · 更新 · 环境 · 隧道 · 系统集成。
**它是唯一接入入口** —— 其它层只调用，不自己碰 `invoke`、不自己碰系统接口。

### 6.1 能力域

| 域 | 能力 |
| --- | --- |
| **凭据** | 令牌的读取 / 写入 / 清除（系统凭据库，见 §4.5）|
| **本地服务** | 启停 / 重启 yao 服务 · 状态查询 · 打开终端（工作目录 = 应用根）|
| **tai** | 路径与版本 · 连通检查 · 服务状态 · 数据目录 · 更新检查与应用 |
| **引擎与包** | 引擎更新 · 包更新与冲突处理 · 第三方工具检查 |
| **环境** | 应用根目录 · ENV 键值读写 · 导入 `.env` 文件 |
| **隧道** | frp 配置读写 · 启停 · 状态 |
| **系统集成** | 目录/文件选择 · 打开 URL · 在文件管理器中显示 · 系统语言 · 本地 IP · 平台信息 |

### 6.2 统一客户端

- **一个外壳，两张面**：CUI（对话与工作台）+ 管理面（服务 · tai · 引擎 · 隧道 · 更新）。
- **本地服务可选**：不起本地服务时连远程服务端（地址来源见 §4.2），起本地服务时用本地地址 —— 切的是地址，不是代码路径。
- **统一管理**：服务端与本地引擎的版本、更新、连接状态集中在一处。
- **首页与管理入口由制品类型定**（见 §5.3）：

| 制品 | 内容 | 首页 | 管理入口 |
| --- | --- | --- | --- |
| `unified` | CUI + yao + tai | CUI | yao · tai |
| `cui` | 仅桌面客户端（**含 Bridge**）| CUI | **无** |
| `web` | 仅 Web（**无 Bridge**）| CUI | **无** |
| `yao` | 仅 yao | yao 管理 | yao |
| `tai` | 仅 tai | tai 管理 | tai |
| `server` | yao + tai | 管理面 | yao · tai |

- **入口按制品内容出现**：不含 yao 的包不给 yao 入口，不含 tai 的不给 tai 入口；`cui` 与 `web` **不给任何管理入口**。
- **`web` 与 `cui` 的区别只在 Bridge**：`web` 制品**桌面能力整块不存在**，`cui` 含。

## 7. 测试

- 层与落位按 `14-testing.md`：纯函数与公共态用**单元层**；**跨宿主差异用浏览器层**（改构建清单的取值，把 web 与 desktop 两种情形各跑一遍）；真实登录与真实数据用**拟人层**。
