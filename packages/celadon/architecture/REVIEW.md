# REVIEW · 交给隔离上下文复核者的代码审核

- **版本**：v1.0
- **最后修改**：2026-10-03 15:36:31
- **说明**：**代码审核** —— 何时用与闭环 · 隔离要求 · 三遍审核（边界与潜在 bug · 规范一致性 · 真实路径与回归，**全部只读**）· **用例审查（专抓假绿）** · 复核者纪律 · 判定口径 · 报告模板 · 验收与标记 · 留档

> **本文是审核规范，不是开发规范。**
> 你在[开发](SPEC.md)中**不读本文**；等你自认为"做完了、没问题了"，才按本文换一双没有成见的眼睛。

## 1. 什么时候用（时机与闭环）

**唯一触发时机**：该批次的功能**开发全部完成**、`SPEC.md` §8 的验证链**全绿**、作者与用户
**都认为没有别的问题了** —— **在决定提交推送之前**，跑一次。

- **开发阶段不跑**：代码还在动时跑，结论很快作废。
  开发中要做的是按 `SPEC.md` §8 验证，**不是**审核。
- **一批一跑**，不按单次改动跑。
- **不许**用审核替代 `SPEC.md` §8 的验证 —— 全绿是**前提**，不是结论。
- 审核的目的**不是复述作者做了什么**，而是找出**作者没想到**的边界与缺陷。

**闭环**：

```
开发 ──► 自认为完成（验证链全绿）──► 审核 ──► 作者逐条处置 ──► 交回验收 ──► 文档标记 ──► 提交推送
         └ 这一阶段不跑审核                        └ 都在 §7，缺一步不算走完
```

## 2. 隔离要求（硬）

| 项 | 要求 |
| --- | --- |
| **上下文** | 复核者**不带作者的历史**：不给聊天记录、不给设计推导、不给作者的解释与结论 |
| **给的资料** | ① 本文 `REVIEW.md` ② [`SPEC.md`](SPEC.md)（规则手册）③ **代码与产物本身** |
| **不给的资料** | 作者的实现说明 · "我已经测过 X 了" · "这里故意这么写" · 任何自评（**唯一例外**：验收轮要作者的**处置表** —— 它是被验对象，见 §7.1；"我做得没问题"这类结论仍不给）|
| **读什么** | 自己读**代码**（含 diff 范围）与产物 · 看**作者留下的**日志与截图 |
| **跑什么** | **`pnpm lint`**（基础语法）· **`pnpm check`**（规范门禁）· **`pnpm test`**（单元）—— 都快，且**必须过** |
| **不跑什么** | **浏览器 · 拟人 · 构建不跑**（要起服务、要真浏览器、要产物，慢）—— 那是作者的活（见 `SPEC.md` §8）；审核的时间花在读代码上 |
| **改什么** | **不改代码** —— 只发现问题、给位置、给证据；修改由作者做 |
| **不递归** | 复核者**不给自己找复核者**，也不要求再开一轮全量审核；一轮审核的终点是 §7.1 的**一次验收**，到此为止。（复核者读 `SPEC.md` 时，跳过它的 §9）|
| **产出** | 一份报告（§6），**每条都带位置与证据**（代码行，或作者交的日志/截图）；报告落 `app/logs/<日期>/`（见 §7）—— 跟项目走，人和 Agent 都看得到 |

> 复核者与作者结论不一致时，**以代码与证据为准**，把分歧原样写进报告。

## 3. 三遍代码审核（不许合并，全部**只读**）

三遍**各查一类**，逐遍出结论。**证据是代码与产物，不是作者的说法。**
每条的写法固定为：**发现 → 位置（`文件:行`）→ 判定（缺陷 / 风险 / 可接受）→ 证据（怎么确认的）**。

### 3.1 第一遍 · 边界与潜在 bug（最重点）

**逐项过，不适用就写"不适用"并说明为什么。不许用"看起来没问题"代替检查。**

| 类别 | 具体要查 |
| --- | --- |
| **空与缺省** | 空数组 / 空字符串 / `undefined` / 缺字段 / 可选参数未传 —— 是否会崩；是否会渲染出 `undefined` / `null` / `NaN` |
| **极值** | 0 · 1 · 上千条 · 超长单行 · 极大数字 · 负数 · 小数精度 · 除零 |
| **下标与索引** | 越界 · 越界前一位 · 空态取首项 · 过滤后为空 · 同时增删导致索引失效 |
| **重复与并发** | 重复点击 · 提交中再点 · 并发请求返回乱序 · 快速切换导致旧响应覆盖新状态 |
| **取消与超时** | 组件卸载后写状态 · 请求取消 · 超时 · 重试是否幂等 · 失败是否留下脏状态 |
| **Unicode 与输入** | emoji · RTL 文本 · 全角标点 · 前后空格 · 大小写 · 中文输入法组合中 · 粘贴多行 |
| **地址与导航** | 深链直接打开 · 刷新 · 后退 · 新标签 · 未知路径 · 缺参数 · **参数重复** · 分享链接是否带命名空间 |
| **时间与时区** | 非本地时区 · 夏令时 · 跨日 / 跨年 · UTC 与本地混用 |
| **网络与存储** | 离线 · 慢网 · 服务端 4xx / 5xx · 响应体非 JSON · 存储被禁用 / 写满 / 旧版本数据 |
| **权限与宿主** | 未登录 · 无权限 · 能力开关为假（Web 上调 `bridge/`）· 宿主缺失 |
| **状态残留** | 切语言 / 切主题 / 切对象 / 换服务地址后，上一条的缓存与草稿是否串过来 |
| **清理与生命周期** | 事件订阅 / 定时器 / 监听是否解绑 · 卸载后回调是否仍会执行 · 是否存在内存增长 |
| **错误处理** | 抛出的错有没有被吞 · 失败路径有没有给用户看得见的反馈 · 异步边界是否都已 await |
| **副作用顺序** | 初始化顺序 · 首帧之前与之后 · 事件顺序（先写 store 还是先写地址栏）|

### 3.2 第二遍 · 与规范的一致性（逐条对 `SPEC.md`）

- 落位对吗？**有没有往上引**（`routes/` → `components/` → `features/` → `stores/` → `data/` → `platform/`）？同层互相 import 业务件吗？
- 命名全称吗？有没有缩写、自造词、与既有词汇冲突？文件角色后缀对吗？
- 用户可见文字**全走语言包**吗？四语齐了吗？代码里有硬编码汉字吗？
- 颜色 / 间距 / 字号 / 圆角有字面值吗？**生成物有没有被手改**？
- URL：只在动作里写吗？有 `useEffect` 里写 URL 吗？**真链接（`appHref`）与路由路径（`to` / `navigate`）有没有混用**？分享链接走了 `buildShareUrl` 吗？
- 状态：改 store 只经动作吗（带动作名）？公共态里有功能词汇吗？值指向对象时用了条目 `{ kind, id }` 吗？
- 宿主差异走能力开关了吗？有没有散落的平台判断？
- 接口类型手写吗？请求有没有绕过 `transport/`？组件里有 `fetch` / `EventSource` / `new WebSocket` 吗？
- 有没有用明确不采用的东西（旧包 · `mobx` · `storex` · `antd` · `lucide-react` · 外部雪碧图 · `@tanstack/react-virtual`）？
- 有没有裸写 `<button>` / `<select>`（`components/base/` 之外）？
- **每条给一个"改前 / 改后"或"符合 / 不符"的具体位置。**

### 3.3 第三遍 · 真实路径与回归（**读，不跑**）

**这一遍靠读代码、读用例、读作者的证据，不靠跑**（跑浏览器与拟人是作者的活，见 §2）。
要回答的只有一个问题：**这条路径有没有被钉住？** —— 对下面每一条，**指出哪条用例覆盖了它**；
找不到就写「**没覆盖**」，并按 §3.4 判断已有用例是不是假绿。

| 路径 | 要找什么 |
| --- | --- |
| 点击 · 全键盘 | 用例是否真的走完（Tab 顺序 · Esc · Enter · **焦点环可见**）|
| **中文输入法** | 有没有 IME 用例：组合中 · 候选词 · **未上屏时回车 / 点击不误提交** |
| 刷新 · 后退 · 深链 · 分享链接 | 各有没有用例；分享链接是否验过"带命名空间 / 别人机器能打开" |
| **两端** | Web 与 Desktop 的差异**是否在平台层消化**（读代码判断，不是跑两端）|
| 深浅主题 · 四语 · 窄窗 · 缩放 | 单元用例或**拟人剧本**是否覆盖（看作者的日志与截图）|
| **渲染结果类**（图标 · 图形）| 断言的是"**真的画出来**"（缩放 · 描边 · 可见性）还是"元素存在" |
| **新增门禁规则** | 是否**同时**补了一个正例与一个违规例 |

- **行为改动没有对应用例 = 缺陷**（"每一行改动都带测试"）——逐条对本次改动列出"哪些行没有用例钉住"。
- **作者写"不补"必须给理由**；**没写理由就是缺陷**。
- 拟人剧本：读它是否按**三段**（剧本 · 修改记录 · 测试记录）· **判定数据执行前冻结** · **截图留档** ——
  看作者的证据文件，不自己跑。
- 最后**列出应该补而没补的用例**，并逐条写明作者为何不补。

## 4. 复核者纪律

1. **只看代码与产物**，不看作者的说法；作者的解释不构成证据。**跑 `pnpm lint` · `pnpm check` · `pnpm test`；浏览器 · 拟人 · 构建不跑**。
2. **不许"看起来没问题"** —— 每条结论要能指出**读了哪一行**，或**看了作者的哪份日志/截图**。
3. **不确定就写"不确定"**并说明缺什么证据；**不许把"看不清"并进"没问题"**。
4. **不改代码**，也不替作者设计替代方案（可以指出方向，不必替写）。
5. **风险要分级**：会导致错数据 / 丢数据 / 安全问题 / 不可逆操作的，单独列在最前面。
6. **结论要能回到同一处代码**：每条给 `文件:行`。

## 5. 判定口径

| 判定 | 含义 |
| --- | --- |
| **缺陷** | 按现有代码一定会出错（含边界条件）；给出触发条件 |
| **风险** | 在特定条件下可能出错，或依赖未写明的假设；写清条件 |
| **可接受** | 查过、确认没问题；写清"查了什么才敢说没问题" |
| **不确定** | 证据不足；写清缺什么、怎么补 |

## 6. 报告模板

```markdown
# 审核报告 · <被审核的范围>

**状态**：未验收 | 已验收（<日期> <时间> · 复核者 <标识>）| 有条件通过（遗留 N 项）

## 审核范围与方式
<审核了哪些文件 / 提交范围 · 读了什么 · 跑了哪三条（`pnpm lint` · `pnpm check` · `pnpm test`）· **当轮日志路径**（`app/logs/<日期>/review-<HHMM>.log`）· 看了作者的哪些日志与截图>

## 高优先级（错数据 / 丢数据 / 安全 / 不可逆）
<逐条：发现 → 位置 → 判定 → 证据>

## 第一遍 · 边界与潜在 bug
<逐条：发现 → 位置 → 判定 → 证据；不适用的类别写"不适用 + 为什么">

## 第二遍 · 规范一致性
<逐条：规则 → 位置 → 符合 / 不符 → 证据>

## 第三遍 · 真实路径与回归（读，不跑）
<逐条：路径 → 结论 → 证据；含"应该补而没补的用例">

## 与作者结论的分歧
<有则写清；没有就写"无">

## 不确定项
<缺什么证据、怎么补>
```


**复核者跑过的东西必须留下**，与其它层日志同一套规矩 —— 落 `app/logs/<系统日期>/`：

| 留什么 | 落哪 |
| --- | --- |
| 跑过的命令与输出 | `app/logs/<日期>/review-<HHMM>.log`（走 `scripts/run-logged.mjs`：屏幕与文件双写、退出码原样透传）|
| 临时探针脚本与其输出 | `app/logs/<日期>/review-probes/` —— 探针**不写进仓库**，不碰 `app/src/` |
| 截图 | 一律走 `scripts/shots.mjs`，落 `app/logs/<日期>/shots/review-<范围>/` |
| **报告** | `app/logs/<日期>/review-<HHMM>.md` —— **与日志同目录同日期**，不另设私仓目录 |

- **整体跟日志一套规矩**：`app/logs/` 按系统日期分目录、git 忽略、保留 14 天（`CUI_LOG_KEEP_DAYS` 可调）。
- **需要长期留存的结论**（状态标记 · 遗留项）写进该批次的工作记录，并在提交信息里指向当轮 `review-<HHMM>.md`。
- **报告里每条结论都要指向当轮日志或截图**（写明文件名）；指不到，就是没留档，**等于没有证据**。
- 复核者**不改仓库**：探针与临时脚本一律放 `app/logs/` 下。
- 需要人裁定的观感问题，截图**嵌进结论**（`![说明](workspace://<workspace-id>/<路径>)`），不要只说"见某文件"。

## 7. 验收与标记（闭环的另一半）

### 7.1 交回验收

作者按报告**逐条处置**（**每条都要给**：已改 / 不改 + 理由），并**重跑 `SPEC.md` §8 的验证链**；
然后把结果**交回同一复核者验收**。复核者**只验处置，不重开全量审核**：

| 项 | 要求 |
| --- | --- |
| 作者交什么 | 报告（含逐条处置）· **修复后重跑的日志**（`app/logs/<日期>/`）· 拟人截图 —— 处置表**必须给**（验收验的就是它）；作者的自我评价仍不给（§2）|
| 复核者做什么 | ① 说"已改"的，**在代码里确实改了**（读实现与用例，判断用例**是否真能失败**）② 说"不改"的，**理由是否成立** ③ 跑 `pnpm lint` · `pnpm check` · `pnpm test`，再读改动周边有没有引入新问题 —— 三者**必须过**；
④ **审用例本身**（§3.4：恒真断言 · 只断言存在 · 抢跑 · mock 掉被测逻辑 · 改动没带用例）—— 这条与读代码同等重要；浏览器 · 拟人 · 构建不跑，作者交的日志与截图就是证据 |
| 结论 | **通过** · **有条件通过**（写清遗留项）· **不通过**（写清哪条未成立）|
| 留档 | 验收日志落 `app/logs/<日期>/review-<HHMM>.log`（同 §8）|

- **不通过**就回到 7.1 再走一轮；**不设轮次上限**，但**每轮都要留档**。
- 需要口味与价值裁定的（观感 · 文案语气 · 视觉风格 · 成本取舍）**转人**，随结论附截图。

### 7.2 文档标记

验收结论**必须写进文档**，不能只留在对话里：

- **报告头部加状态行**：`已验收（<日期> <时间> · 复核者 <标识>）` 或 `有条件通过（遗留 N 项）` 或 `未验收` ——
  状态改动**在报告里原地更新**，并在该批次的工作记录里同步一行。
- **遗留项逐条写清**："为什么留着 · 在什么条件下处理" —— **不许写"以后再说"**。
- 该批次的工作记录里**指向 `app/logs/<日期>/review-<HHMM>.md`** 与它的状态。
- **状态不是"已验收"（或有条件通过）的批次，不进提交推送。**

## 8. 留档（验证结果按日期落 `app/logs/`）
