# architecture/ — CUI 2.0 架构规范

> **本目录回答**：代码怎么组织、依赖往哪个方向走、边界在哪、什么不许写。
> **与邻居的分工**：
> - [`../design/`](../design/) 管**长什么样**（token · 排版 · 图标 · 组件外观）—— 视觉唯一来源；
> - **`architecture/`（本目录）** 管**代码怎么摆**（分层 · 依赖方向 · 数据流 · 宿主边界 · 工程门禁）；
> - [`../plan/`](../plan/) 管**做到哪了**（阶段 · 状态 · 验收 · 依据）—— 过程与决定，不是规则。
>
> **三者不重叠**：视觉规则不在本目录复述，计划状态不在本目录记录。

## 写法

**读者是 Agent**：只写**会改变行为**的规则。
- 动机、历史、取舍过程 → `.agent/worklogs/`，不写在这里。
- 一条规则只在一处写全，别处给编号引用。
- 用表格与短句；示例只留能照抄的形状。

## 怎么读

**写作标准**（这三条决定了这里的文档长什么样）：

- **写规则，不写现状**：**app 代码会被重置**，所以「目前只有 X」「现在走的是 Y」这类句子迟早变假 ——
  只写"该怎么做"、"允许什么/禁止什么"。现状与进度放 `plan/`。
- **举例用通用名**（`inbox` · `chat` · `data-table`），**不要引用真实脚手架**（写死某个页面/组件名）。
- **理由只在推不出来时才写**，其余给指向具体文件的指针。
- **不写「待讨论」**：开放问题写成"该怎么做"（指南），或写成"不做 + 为什么"（不做的部分）；
  进度与未决事项放 `plan/`，架构册只留结论。
- **每册要写全明细**：一个概念的所有分支（如状态的私有 / 公共）都在同一处写清，别让读者去别的册拼。
- **通用格式**（`00-principles.md` 是样板，照抄，不许自创）：

```
# <编号> · <名>
- **版本** / **最后修改** / **说明**

## 1. <本册的硬规则>      列表，一条一句
## 2. <主题>              章首一句话总纲；**定义**用类型 / 图 / 表给出
### 2.1 <分支>
## n. …                  编号即可引用；结论先行，细则往后
```

  - **规范只写定义与规则**：类型 · 字段 · 允许值 · 禁止事项。**不写实现细节**（`undefined` · 初始值 ·
    某段代码怎么写），也不叙述现状。
  - **能表格就表格**，别写成散文。
  - **名字由规范给**：类型名 · 字段名 · 概念名都在规范里写明，**代码照它实现**；
    实现里先起个名字、规范里没提，读者会把一件事当成两件。
  - **别引用 `plan/` 的内容**（`plan/` 是过程文档，会删）：规则写进架构册，`plan/` 只提"目录本身"
    （如"进度放 `plan/`"）。同理，**引用的路径要能长期存在**。
  - **标题与正文用规范用语**：构成 · 落位 · 归属 · 约束 · 边界 · 关系。
    不用口语（"长什么样" · "放哪" · "要不要…" · "怎么办"）。

## 一条铁律

**视觉规则只在 `design/` 定，工程规则只在本目录定。** 两边都不许在代码里出现"第三份真相"。
