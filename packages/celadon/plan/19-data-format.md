# 19 · 数据格式（Data format）

- **状态**：🚧 起草 —— 已定的规则先落；显示细节随第一个真正用到它的页面推进
- **范围**：日期与时间 · 时区 · 相对时间 · 数字与千分位 · 单位 · 货币 · 文件大小 · 复数与列表 · **双向文本（RTL）**
- **不包含**：界面文案与语气（→ `14 内容与文案`）· 组件的呈现形态（→ `03 组件`）· 图表内部格式（→ `15 数据可视化`）
- **依赖**：后端接口时间契约（见 §2）· i18n 运行时（`design/i18n/*`）

> **一句话原则**：**存的是事实，显示的是习惯。** 事实（时间戳 · 数值 · 标识）不随语言变；习惯（写法 · 单位 · 顺序）随语言变。

## 1. 四条铁律

| # | 规则 | 说明 |
| --- | --- | --- |
| **1** | **显示跟用户语言走**，不跟数据来源走 | 用户切到日文，看到的就是日文的日期写法；数据从哪来不影响显示 |
| **2** | **存储一律 UTC** | 后端接口统一 UTC；客户端按本地时区渲染，**不做**"偏移量加减"的手工运算 |
| **3** | **客户端时区随请求上送** | 不能只在渲染时用 —— 服务端也要按"用户当地的今天"做判断（今日 · 本周 · 定时 · 相对时间） |
| **4** | **数据本身不翻译** | 模型名 · 文件名 · 代码标识 · 用户输入 · 时间戳原始值 —— 这些是数据，不是文案（与 `design/i18n` 的"不翻译清单"同一条） |

## 2. 时区契约（已定）

**传输**：客户端把 `clientTimeZone` 随请求一起上送。

**只接受两种值**，其余拒绝：

```
UTC
IANA Area/Location      ← 如 Asia/Shanghai、America/New_York
```

**必须规范化（拒绝别名）**：像 `Asia/Calcutta`、`US/Pacific` 这种历史别名要归一成 `Asia/Kolkata`、`America/Los_Angeles`。

> **为什么这一点必须硬**：时区会落到**持久记录**上，之后由**另一个进程**再解析。这一步接受别名，将来跟同一时刻对不上 —— 只要写过一次，就再也没法可靠比较。

**多时区**：同一轮请求里如果出现多个不同时区，标记为 `mixed` 并**不做猜测**（例如用户在旅途中切换网络）。

**落库时间戳**（带偏移 + IANA 括注，人可读且机器可解析）：

```
2026-09-30T16:12:34+08:00[Asia/Shanghai]
```

**渲染**：一律用运行时的格式化能力（`Intl.DateTimeFormat` / `Intl.NumberFormat` / `Intl.RelativeTimeFormat`），**不手写**日期拼接与千分位。

## 3. 显示规则

| 项 | 规则 | 备注 |
| --- | --- | --- |
| 日期 | 跟语言的常规写法（`2026-09-30` / `30/09/2026` / `2026年9月30日`） | 用 `Intl` 的 `dateStyle` 档位，不逐语言手写模板 |
| 时间 | 24 小时制优先；需要时按语言切 12 小时制 + 上午/下午 | 同一界面内**不混用**两种制式 |
| 相对时间 | 「3 分钟前 / 2 天前」**跟语言**（含复数：`1 minute` / `2 minutes`） | 超过约 7 天退化为**绝对日期** |
| 数字 | 千分位与小数点符号跟语言（`1,234.5` / `1.234,5`） | 用 `Intl.NumberFormat` |
| 单位与文件大小 | `1.8 MB` · `12 页` · `2.1 KB` | 单位符号可本地化（`页` / `pages` / `ページ`） |
| 货币 | 符号与位置跟语言/地区（`¥1,280` / `$1,280`）；金额**不做四舍五入的二次加工** | 币种本身是数据，不翻译 |
| 时长 | `1:23` / `2 小时 5 分` —— 语义不同场合不同：**进度用 `1:23`**，**陈述用时用文字** | 同一处不要两种混用 |
| 复数 | 需要复数形式的语言走 `Intl.PluralRules` 或等价能力 | 中文/日文无复数变化 |

> **数字与单位不是"文案"**：`1.8 MB`、`3 未读`、`2 / 4` 这类里只有**单位词**需要翻译，数字本身不翻。

## 4. 双向文本（RTL）

**结论：暂不新增 RTL 语言，但从现在起布局只用逻辑属性。**

- **收益**：RTL 覆盖阿拉伯语 · 波斯语 · 希伯来语 · 乌尔都语市场。同类 AI 客户端里，有的已支持 19 种语言（含阿拉伯语、波斯语），有的只做中英双语 —— **做与不做都有先例**
- **成本**：整站布局要逻辑属性化 + 图标/箭头镜像 + 数字与日期 + 双向混排（bidi）+ 全量回归。**事后改贵，事前几乎免费**
- **现状实测**：本包三张页面共 **45 处物理方向**（`margin-left` 16 · `left:` 22 · `padding-left` 2 · `text-align: left` 1 · `border-left/right` 2 …），**逻辑属性 0 处**
- **现在只做一件事**：把这些换成逻辑属性 —— 一次性、成本很小、以后要不要 RTL 都随时能开

| 物理写法 ✗ | 逻辑写法 ✓ |
| --- | --- |
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-left` / `padding-right` | `padding-inline-start` / `padding-inline-end` |
| `left: 0` / `right: 0` | `inset-inline-start: 0` / `inset-inline-end: 0` |
| `text-align: left` / `right` | `text-align: start` / `end` |
| `border-left` / `border-right` | `border-inline-start` / `border-inline-end` |
| `border-top-left-radius` 等 | `border-start-start-radius` 等 |

**具体怎么写、哪些例外可以保留物理方向** → 见 [`../CONVENTIONS.md`](../CONVENTIONS.md) §3（CSS / LESS 编码规范）。
效果演示（可切 RTL 对照）→ `design/css-logical.html`。

> 本节只保留**决策**：现在不新增 RTL 语言，但从第一行产品代码起只用逻辑属性。

## 5. 若要支持 RTL：成本记录（**暂不启动**，仅备查）

> 触发条件：出现明确的中东客户 / 市场计划。届时按本节估算拍板，不用重算。

**一次性开发**

| 项 | 现在做（产品代码未写） | 事后补（产品已写完） |
| --- | --- | --- |
| 布局逻辑属性 | **0**（规矩已立，见 `../CONVENTIONS.md` §3） | 全站逐条改 5–15 人日 |
| 方向性图标镜像（本包 7 个） | 0.5 | 1–2 |
| 数字 / 日期 / 日历 | 1–2 | 2–3 |
| bidi 混排 | 1–2 | 3–5 |
| 组件逐个过（下拉 · 抽屉 · 表格 · tooltip · 滚动条 · 拖拽把手） | 2–3 | 5–10 |
| 测试与走查 | 2–3 | 3–5 |
| **小计** | **≈ 7–12 人日** | **≈ 19–40 人日** |
| 翻译（`ar` + `fa`，走 AI + 术语表 + 抽检） | +1–2 | +1–2 |
| **合计** | **≈ 8–14 人日（2–3 周 / 1 人）** | **≈ 20–42 人日** |

**长期开销（比一次性更重，且与语言数成正比）**

| 项 | 量级 |
| --- | --- |
| **测试面 ×2**（每个界面 LTR / RTL 各一遍，每次改版都要） | **最大的一项** |
| 每加一个组件都要在 RTL 下走一遍 | 永久 +10–20% 组件工时 |
| 文案溢出复查（阿语通常比中文长 30–50%） | 每个新界面 |
| 用户支持（阿语工单，团队未必有人能读） | 视市场而定 |

**两条已经查证的事实**

1. **翻译不是大头** —— 现在四语本就是 AI 翻译；`ar` / `fa` 同理，成本主要是**术语表 + 抽检**，不是逐句人工
2. **最贵的一块已经免费拿到** —— 布局逻辑属性（5–15 人日）已通过编码规范前置解决
