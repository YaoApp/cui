# 12 · 测试

> **测试分三层，判定依据不同**：单元/组件测与浏览器测由**确定性代码**判；
> 拟人测试由**执行者依据证据初判、人终审** —— **禁止的是无证据的判定，不是判定本身**。
> 三层不重叠、不互相替代 —— 上层能发现的问题，下层不一定能；反之亦然。

---

## 1. 分工总表

| 层 | 工具 | 判定者 | 测什么 | 不测什么 |
| --- | --- | --- | --- | --- |
| **单元 / 组件** | `vitest` · `@testing-library/react` · `user-event` · `jsdom` | 确定性代码 | 纯逻辑 · 状态与数据层 · 组件行为（键盘 · 焦点 · 表单校验 · 加载/错误态）| 真实网络 · 真实渲染引擎差异 · 观感 |
| **浏览器** | `@playwright/test` + 截图 golden | 确定性代码 | 关键交互主路径 · 中文输入法 · 全键盘 · 视觉回归（像素比对）| 主观观感 · 措辞是否别扭 |
| **拟人** | 剧本 + 浏览器执行 + **AI 看证据初判** | **AI 初判 · 人终审** | 真实使用路径 · 人味清单 · 极端数据 · 环境差异 · 观感与措辞 | 不做**无证据**的判定 |
| **规范门禁** | 现有 `scripts/tests/`（**零依赖**）| 确定性代码 | 设计规范（token · i18n · 样式约定 · 文档结构）| 应用行为 |

**规范门禁与应用测试并存，不混** —— 前者零依赖、随设计资产走；后者用上表的栈。

---

## 2. 单元 / 组件测试

**栈**：`vitest`（运行器）· `@testing-library/react` + `@testing-library/user-event`（组件行为）· `jsdom`（DOM 环境）· `@vitest/coverage-v8`（覆盖率）。

**位置与命名**：`*.test.ts(x)`，**与组件 / 页面同目录** —— **一个组件一个目录，测试放在该目录内**（与源码并列）。
目录结构本身如何分层、公共组件归属，见 `02 布局`。

**测什么**：

1. **从旧仓库搬入的模块必须有测试** —— 它们经过四道工序改造（换 UI 底座 · 换 i18n · 换状态 · 去旧依赖），行为必须被锁住
2. **状态与数据层必须有测试** —— 含请求封装（`openapi/` 子集）· 校验 · 格式化 · store
3. 组件行为**断言用户看到什么**（可见文字 · 角色 · 可访问状态），**不测实现细节**（不测内部 state、不测私有方法、不依赖 class 名）

**mock 边界**：

| 层 | 处理 |
| --- | --- |
| 网络 | **mock 掉**（flake 头号源头是"真后端"）|
| 时间 | **冻结**；动画用假时钟推进 |
| 存储 | 内存实现 |
| 真实渲染引擎 | **不 mock** —— 这类差异交给浏览器层 |

**覆盖率**：**不设阈值**。数字是长期投入的结果，不是起步条件；覆盖率用于**发现盲区**，不用作验收。

**不做的**：

- 不为"看起来完整"给纯展示组件写测试
- 不写只重复实现逻辑的测试（断言与实现同一份推理）
- 不用快照测试替代行为断言（快照通过 ≠ 行为正确）

## 3. 浏览器测试

**工具**：`@playwright/test`。同时承担两件事：**关键交互回归** 与 **验证 UI 底座能力**。

**主路径清单（先这 10 条，稳定后扩展）**：

| # | 路径 | 要点 |
| --- | --- | --- |
| 1 | 登录 / 登出 | cookie 鉴权 · 失败提示 |
| 2 | 切换到某个会话 | 会话列表 → 消息区 · 滚动位置恢复 |
| 3 | 发送一条消息 | 流式接收 · 贴底 · 输入框清空 |
| 4 | 会话内向上加载更早历史 | 反向无限滚动 · 不清屏跳动 |
| 5 | 新建 / 重命名 / 删除会话 | 侧边联动 · 乐观更新的回滚 |
| 6 | 收件箱列表操作 | 已读 / 收藏 / 跳转会话 |
| 7 | 看板列内拖动 / 移动 | 落点正确 · 刷新后保持 |
| 8 | 专家列表筛选与进入 | 搜索 · 空态 |
| 9 | 配置页改一项并保存 | 表单校验 · 保存反馈 |
| 10 | 刷新与后退 | 路由与状态不串 |

**UI 底座的验收项**（一次性，验收后并入回归）：

1. **中文输入法** —— 组合中输入 · 候选词选择 · **未上屏时按回车/点击**不误提交
2. **全键盘** —— Tab 顺序 · Esc 关闭 · Enter 提交 · **焦点环可见**
3. **Celadon token 生效** —— 组件跟随 token 换肤（深浅色）而非硬编码样式

**选择器**：**语义优先** —— 用用户看到的文字 / 角色 / 可访问名；**只有无稳定文字时才加测试 id**（图标 · 列表项）。理由：语义选择器测的是用户看到的东西，抗重构。

**稳定性三招**：

| 源头 | 做法 |
| --- | --- |
| 数据 | mock 后端 · 固定种子数据 |
| 时间 | 冻结时钟；动画用 `mainClock.advanceTimeBy()` 推进，**不用 sleep** |
| 同步 | **等条件**；断言可见性前**先 `waitForIdle()`** |

**flake 治理**：不稳定测试**隔离**（目标 flake < 1%）· **禁止盲重试掩盖** —— 必须写根因分诊结论。

**视觉回归**：**截图 golden** —— 固定状态 + 冻结时间 + 像素比对；**不用 LLM 判断**。新增/修改视觉时**人工确认后更新基线**，基线变更进提交记录。

**运行环境**：按目标运行时逐个跑 —— 桌面浏览器（Chromium / WebKit）+ **桌面壳的 WebView** + **移动端 PWA**。
（各引擎的支持度差异要在这里发现，不能只测一个。）

## 4. 拟人测试（AI 测试）

**为什么单独一层**：开发与测试由**同一个 Agent** 完成，最大的风险是**自我确认** ——
测试按实现写、断言按现有行为写，于是"全绿"但用户一用就坏。

**铁律（AI 测试的真实边界）**：

| 结论 | 约束 |
| --- | --- |
| **自动**运行的 LLM 定位器**会愈合到错的元素**（**静默错判**）| 禁止**无人复核**的自动判定；判定必须有证据、可复核 |
| UI 视觉 agent 中文界面识别约 60% · 小按钮点不中 · 长链条成功率指数衰减 | 不把"看一眼说没问题"当验收；**长链条拆成短链**逐步验证 |
| 视觉测试能精确落地的形态 = **截图 golden** | **像素级**回归走 golden；**语义/观感**回归由执行者看截图判 |

**读法**：这张表的约束对象是**「无证据、无人复核的自动判定」**，不是"能不能判"。
执行者有浏览器与视觉能力，**可以也应当下判断** —— 但判断必须落在证据上、且可被复核。

**LLM 只出题，不出判**：生成候选剧本 · 从截图里提疑点 · 整理执行记录。

### 4.1 角色分离（核心）

1. **只看验收标准，不看实现** —— 从各模块计划的验收条款出发，不从代码出发
2. **先写剧本，再执行** —— 剧本用**用户语言**（"我想改一下会话标题"），不写函数名 / 选择器
3. **预期在执行前写死**，不许看完再补
4. **证据是外部产物** —— 截图 · 录屏 · 执行记录 · DOM 片段；**"我验证过了"不算证据**

### 4.2 人味清单（作者不会做、用户天天做）

| 类别 | 动作 |
| --- | --- |
| 中文输入 | 输入法组合中 · 候选词 · 中英混输 · 全角标点 · **未上屏时回车 / 点击** |
| 全键盘 | Tab 顺序 · Esc 关闭 · Enter 提交 · **焦点环可见** · 不用鼠标走完主路径 |
| 乱来 | 重复点 · 提交中再点 · 中途刷新 · 后退 · 断网 · 关掉再开 |
| 极端数据 | 空态 · 只有 1 条 · 上千条 · 超长单行 · emoji · 纯英文 / 纯数字 / RTL 文本 |
| 环境 | 深浅色 · 缩放 125% / 150% · 窄窗 · 慢网 · 非本地时区 |
| 跨会话 | 切换后状态是否串 · 刷新后滚动位置与输入草稿 |

### 4.3 触发时机

| 时机 | 范围 |
| --- | --- |
| 一个页面 / 模块完成 | 该模块的拟人剧本 |
| 每次提交前 | 与本次改动相关的剧本 |
| 版本发布前 | **第 3 节的主路径清单**，全量走一遍 |

### 4.4 产出物

每次执行后在**工作区内部**留档（不进公开仓库），含：**剧本**（执行前写死的预期）· **执行证据**路径 ·
**结论**（通过 / 失败 / **看不清** —— 看不清必须写，不许并进"通过"）· **新发现**（真实失败回流成固定用例）· **flake 记录**（根因）。

---

### 4.5 判定怎么做（执行者初判 · 人终审）

**判定用三件，够用且互补** —— 各自弱的地方正是别人强的地方：

| 手段 | 强在哪 | 弱在哪 |
| --- | --- | --- |
| **看截图**（原生视觉）| 布局 · 状态（空 / 满 / 错）· 是否塌 · 观感是否别扭 | 精确文字与数字不可靠 |
| **OCR** | 文字与数字**逐字精确** · 表格 · 手写 | 看不出"哪里不对劲" |
| **决策模型**（分类 / 评分 / 度量，**带置信度**）| 给出**明确结论**（通过 / 不通过 / 需人看）| 需要先把输入整理干净 |

**判定流程**：**看图发现问题 → OCR 确认文字与数值 → 决策模型给分级结论与置信度**。
判定必须能回到**同一张截图 + 同一步操作**，别人能重走。

**置信度是门控，不是保证**：

- **高置信度可用，低置信度必须转人** —— 阈值是**路由策略**，不是正确率承诺
- **概率 ≠ 正确率**：模型自报的高分区间里仍有错判
- 因此**人终审不省** —— 决策模型负责分流，最终裁定在人

**四条要求**：

1. **依据验收标准，不依据实现** —— 判"符不符合承诺"，不是"跟代码符不符"
2. **判断必须落在证据上** —— 截图 · 执行轨迹 · DOM 片段 · OCR 文本；**没有证据的判断一律作废**
3. **结论可复核** —— 写清"看的是哪一屏哪一步"，让人能重走一遍
4. **不确定就写"看不清"** —— 不许把模糊印象写成结论

**能力边界**：

| 可判（有证据）| 必须留给人 |
| --- | --- |
| 控件能否点中 · 焦点是否可见 · 键盘能否走完 · 输入法是否误提交 | **"别扭不别扭"的最终裁定** |
| 空态 / 加载 / 错误 / 满态是否出现且不塌 | 文案语气与品牌调性 |
| 布局是否溢出 · 是否被裁切 · 对比度是否达标（可测数）| 视觉风格取舍 |
| 与验收条款逐条对照 | 是否值得为观感付出更多成本 |

**长链条要拆开** —— 一步一截图一判断，**不把"从头跑到尾都没事"当作通过**。

## 5. QA 流程（阶段门禁）

**一条直线，阶段不许跳**；**每一阶段的判据在开工前写死**（否则就是"看完再定标准"，即自我确认）。

### 5.1 六个阶段

| # | 阶段 | 做什么 | 通过标准（先写死）| 不过怎么办 |
| --- | --- | --- | --- | --- |
| 1 | **单元 / 组件测试** | 写测试 → 跑通 | 全绿 · 覆盖本阶段改动的行为 | 改实现或改测试 —— **不许跳过** |
| 2 | **浏览器测试** | 写用例 → 跑通 | 相关主路径全绿 · 无新增 flake | 隔离并写根因 —— **不许盲重试** |
| 3 | **剧本 + 判定数据** | 写剧本（用户语言 + 预期）与结构化判据 | 剧本与判据**在执行前冻结** | 补写 —— **不许事后改预期** |
| 4 | **拟人执行** | 按剧本走浏览器，**逐步截图** | 每步有截图与结论 | — |
| 5 | **AI 看图 + OCR + 决策验证** | 看图发现问题 → OCR 核文字数值 → 决策模型给分级结论 | 结论为**通过** | 结论为"需人看"→ 转阶段 6；"不通过"→ 回阶段 1 或 2 |
| 6 | **人终审** | 人看证据与结论 | 明确通过 | 回退到对应阶段 |

**六个阶段都通过才算 OK。** 任一步不过 → **回到对应阶段** —— 不许"留到下一阶段补"。

### 5.2 决策模型在浏览器测试里的用法

| 用途 | 输入 | 输出 | 注意 |
| --- | --- | --- | --- |
| **失败分诊** | 失败截图 + 用例名 + 执行轨迹 | 真失败 / 环境问题 / 看不出 | **只分流，不结案** |
| **视觉基线变更** | 旧基线 + 新截图 + 本次改动说明 | 预期变化 / 疑似回归 | 基线变更**仍需人确认** |
| **覆盖缺口** | 本模块验收条款 + 已有用例清单 | **未覆盖的条款清单** | 只出清单，不判"够了没" |

### 5.3 三条不许

1. **不许事后定标准** —— 判据在执行前写死
2. **不许盲重试** —— flake 隔离 + 写根因
3. **不许把"看不清"当通过** —— 看不清就是看不清，转人

### 5.4 门禁矩阵

| 时机 | 必须走到哪一阶段 |
| --- | --- |
| **每次提交** | 阶段 1（受影响部分）+ 阶段 2（相关用例）|
| **合并到主干** | 阶段 1–2 全绿 + **至少一条剧本走到阶段 5**（证据与结论留档）|
| **版本发布** | **阶段 1–6 全量**：主路径清单全跑 + 视觉基线确认 + 人终审 |

## 6. 待讨论

以下问题**尚未决定**，在"测试"专题讨论中逐个拍：

| # | 问题 | 备选 / 倾向 |
| --- | --- | --- |
| 1 | 从旧仓库搬入模块的测试，**先写测试还是先搬** | 倾向：**先搬可运行的最小子集，立刻补测试**（搬的过程本身会变） |
| 2 | 组件测试的**深度到哪一层** | 倾向：只测行为与可访问性；不测内部结构 |
| 3 | 视觉黄金基线的**维护成本**能否接受 | 待估：哪些页面值得上 golden，哪些只做冒烟 |
| 4 | 浏览器测试的**引擎矩阵**（桌面浏览器 / 桌面壳 WebView / 移动端 PWA）| 待定：至少哪几套 |
| 5 | 拟人剧本**谁写、写多少、多久一次** | 倾向：AI 起草 + 人确认预期；每模块 1–2 条 |
| 6 | "看不清"的**判定标准** | 待定：需要可操作的判据 |
| 7 | LLM 提疑点的**使用方式**（多模态看截图）| 倾向：只用于生成候选问题清单，不进结论 |
| 8 | 新失败回流的**流程与责任人** | 待定 |
| 9 | 拟人测试记录**放哪**（工作区内部文档 vs 提交记录）| 倾向：工作区内部，提交记录只留结论摘要 |
| 10 | CI 上跑什么、本地跑什么 | 待定 |
